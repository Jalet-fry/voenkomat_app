# Спецификация требований к лабораторным работам №7-9 (на базе №1-3)

## Лабораторная работа №7: Разработка серверной части (на базе ЛР №1)

### 1. Технические требования
- **Архитектура:** Серверная часть реализована в виде HTTP-сервера.
- **Протокол:** Тела ответов и запросов представлены в формате JSON.
- **Взаимодействие с БД:** Работа осуществляется с использованием библиотеки `libpq` (или эквивалентных оберток для прямого доступа к PostgreSQL).
- **Ролевая модель:**
    - **Пользователь:** Просмотр, сохранение результатов запросов, редактирование всех таблиц, кроме справочных.
    - **Суперпользователь (Admin):** Все права пользователя + редактирование справочных таблиц + создание бэкапов БД. Требуется ввод пароля ("admin").
- **Категории таблиц:**
    - **Справочники (LookUp Tables):** `fitness_categories`, `commissioners` (ранее positions, groups и т.д.). Содержат неизменяемые данные.
    - **Основная таблица:** `conscripts` или `medical_examinations` (ранее lessons). Содержит динамические данные.

### 2. Спецификация API
- **Методы:**
    1. `GET` – получение данных;
    2. `POST` – создание новой записи;
    3. `PUT` – обновление существующей записи;
    4. `DELETE` – удаление записи.
- **Endpoints:** `/api/conscripts`, `/api/commissioners`, `/api/fitness_categories`, `/api/medical_examinations`, `/api/military_id_cards`, `/api/service_record_cards`, `/api/callup_events`, `/api/conscripts_commissioners`.

### 3. База данных
- Наличие скриптов для создания пустой БД.
- Первичное наполнение справочников.
- **Генератор данных:** Наполнение больших таблиц объемом в несколько сот записей (200+).
- Наличие триггеров и функций (аудит, валидация дат).

## Лабораторная работа №8: Разработка пользовательского интерфейса (на базе ЛР №2)

### 1. Принципы UI (CUA Standard)
- **Классический стиль:** Статические диалоговые окна и меню.
- **Управление клавиатурой:** Основное управление — клавиатурные события. События мыши транслируются в клавиатурные.
- **Отклик:** Время отклика интерфейса на событие не более 0,1 с.
- **Транзакционность:** Без подтверждения ничего не происходит.
- **Формы:** Информация в окнах типа «Форма» не скроллируется.
- **Здоровье оператора:** Приоритет над эстетикой (высокий контраст, читаемость).

### 2. Горячие клавиши
- `Ctrl+A`: Добавление записи (Add).
- `Ctrl+V`: Просмотр данных активной таблицы (View).
- `Ctrl+D`: Удаление записи (Delete).
- `Ctrl+U`: Обновление записи (Update).
- `Ctrl+Q`: Выполнение специального запроса (Queries).
- `Ctrl+S`: Сохранение результата последнего запроса (Save).
- `Ctrl+B`: Создание бэкапа БД (Backup).
- `Ctrl+E`: Выход из приложения (Exit).
- `F10`: Вызов меню.
- `Alt + [Подчеркнутая буква]`: Открытие конкретного меню.

### 3. Навигация и Диалоги
- `Tab / Shift+Tab`: Перемещение между полями (вперед/назад).
- `Arrows`: Перемещение внутри полей.
- `Enter (OK)`: Принятие изменений.
- `Esc (Cancel)`: Сброс изменений / закрытие окна.
- **Меню:**
    - `File` (Alt+F): Минимум команда Exit.
    - `Tables` (Alt+T): Выбор активной таблицы.
    - `Operations` (Alt+O): Список действий (View, Add, Update, Delete, Queries, Save, Backup).

## Лабораторная работа №9: NoSQL база данных и конвертер (на базе ЛР №3)

### 1. Требования к конвертеру
- **Тип:** Консольное приложение.
- **Функция:** Конвертация данных из PostgreSQL в BerkeleyDB.
- **Формат хранения (Key-Value):**
    - **Key:** Первичный ключ (PK) из таблицы PostgreSQL.
    - **Value:** Сериализованные в JSON значения всех остальных столбцов.
- **Составные ключи:** Для таблиц типа M2M (например, `conscripts_commissioners`) ключ формируется как `{id1}_{id2}`.

### 2. Алгоритм
1. Подключение к PostgreSQL.
2. Получение метаданных (имена таблиц, столбцы) через `information_schema`.
3. Создание баз данных BerkeleyDB (.db файлы) для каждой таблицы.
4. Построчное заполнение и закрытие соединений.
