## ВВЕДЕНИЕ

Разработка баз данных является ключевым аспектом построения информационных систем, обеспечивающих хранение, управление и обработку данных.

В данной лабораторной работе рассматривается процесс создания схемы базы данных для модели «Военкомат». Эта модель включает основные объекты, такие как призывники, военно-учётные карты, военные билеты, медосвидетельствования, категории годности, военные комиссары, призывные мероприятия и вспомогательные связи между ними. Реализация данной базы данных позволит организовать эффективное хранение и управление информацией о работе военкомата.

**Цель работы** – создание базы данных, соответствующей построенной реляционной модели, путем написания SQL-запросов для создания и наполнения таблиц.

В ходе выполнения работы особое внимание уделяется правильности построения первичных и внешних ключей, каскадным операциям обновления и удаления, а также соблюдению бизнес-правил. Полученные результаты позволяют протестировать корректность структуры базы данных и проверить работоспособность ссылок между объектами.

## 1 ИСХОДНЫЕ ДАННЫЕ

1. Создать в СУБД новую схему данных для хранения пользовательских объектов (см. часть 2).

2. В этой новой схеме данных с помощью скрипта с запросами на языке DDL SQL реализовать таблицы, соответствующие реляционным отношениям схемы данных полученной в лабораторной работе №2-3, с помощью одного (желательно) оператора CREATE TABLE для каждой таблицы в следующем порядке:

   - реализовать простую структуру таблиц, включающую только набор столбцов с добавлением описаний первичного ключа;
   - дополнить описание таблицы реализацией ограничений для описания внешних ключей; для внешних ключей установить свойства контроля целостности данных (каскадное удаление и обновление), если это возможно в целевой СУБД;
   - дополнить описание таблицы реализацией ограничений для описания бизнес-правил;
   - дополнить описание таблицы реализацией комментариев для значимых элементов таблицы.

3. Заполнить с помощью SQL-скрипта с использованием оператора INSERT таблицы строками данных для проверки правильного выбора первичных ключей и работоспособности ссылок между таблицами:

   - строками данных сначала заполнять мастер-таблицы (или таблицы, которые НЕ ссылаются на другие таблицы);
   - в каждую таблицу добавить N строк осмысленных данных (N – количество строк, выдаваемое преподавателем, в нашем случае 10);
   - если не удается добавить данные в таблицу по причине нарушения уникальности первичного ключа, то следует перепроверить описание этого первичного ключа и его смысл для реального мира;
   - если не удается добавить данные в таблицу по причине нарушения ссылочной целостности, то следует убедиться, что целевые данные существуют, иначе перепроверить описание внешнего ключа.

4. Рассмотреть простые действия по изменению структуры таблицы (переименование столбца таблицы, добавление и удаление ограничений на столбец таблицы или всю таблицу) и реализовать их с помощью оператора ALTER TABLE.

5. Создать временную таблицу с помощью оператора CREATE TABLE и удалить ее с помощью оператора DROP TABLE.

6. Экспортировать результаты работы в SQL-скрипт (см. часть 2), сравнить полученный скрипт со скриптами, созданными на этапах 2 и 3.

## 2 СОЗДАНИЕ ТАБЛИЦ

В рамках реляционной модели «Военкомат» предусмотрены следующие таблицы и соответствующие им сущности.

**Таблица Prizivnik** соответствует сущности призывника и включает поля:
- `prizivnik_id` (уникальный идентификатор призывника)
- `fio` (ФИО)
- `data_rozhdeniya` (дата рождения)
- `adres_prozhivaniya` (адрес проживания)
- `nomer_pasporta` (номер паспорта)
- `voennyi_bilet_id` (ссылка на военный билет, внешний ключ)
- `voenno_uchetnaya_karta_id` (ссылка на военно-учётную карту, внешний ключ)

**Таблица Comissar** отражает сущность должностного лица и содержит поля:
- `comissar_id` (уникальный идентификатор комиссара)
- `fio` (ФИО)
- `dolzhnost` (должность)
- `stazh_raboty` (стаж работы)
- `kontaktnyi_telefon` (контактный телефон)

**Таблица Voenno_Uchetnaya_Karta** соответствует сущности документа учёта и включает поля:
- `karta_id` (уникальный идентификатор карты)
- `nomer_karty` (номер карты)
- `data_postanovki_na_uchet` (дата постановки на учёт)
- `istoriya_otsrochek` (история отсрочек)
- `voenno_uchetnaya_specialnost` (ВУС)
- `prizivnik_id` (ссылка на призывника, внешний ключ)

**Таблица Med_Osvidetelstvovanie** представляет сущность оценки здоровья и содержит поля:
- `osvidetelstvovanie_id` (уникальный идентификатор)
- `data_provedeniya` (дата проведения)
- `rezultaty_obsledovaniya` (результаты обследования)
- `fio_vracha` (ФИО врача)
- `zaklyuchenie` (заключение)
- `prizivnik_id` (ссылка на призывника, внешний ключ)
- `kategoria_id` (ссылка на категорию годности, внешний ключ)

**Таблица Kategoria_Godnosti** соответствует справочнику категорий и включает поля:
- `kategoria_id` (уникальный идентификатор)
- `nazvanie_kategorii` (название категории: А, Б, В, Г, Д)
- `opisanie_ogranichenii` (описание ограничений)
- `index_kategorii` (индекс категории)
- `osnovanie_dlya_kategorii` (основание для категории)

**Таблица Voennyi_Bilet** отражает сущность документа, подтверждающего статус, и содержит поля:
- `bilet_id` (уникальный идентификатор)
- `nomer_bileta` (номер билета, уникальный)
- `data_vydachi` (дата выдачи)
- `voinskoe_zvanie` (воинское звание)
- `kategoria` (категория годности)
- `prizivnik_id` (ссылка на призывника, внешний ключ)

**Таблица Prizivnoe_Meropriyatie** соответствует сущности мероприятия и включает поля:
- `meropriyatie_id` (уникальный идентификатор)
- `tip_meropriyatiya` (тип мероприятия: явка, медосмотр, отправка и т.д.)
- `data_provedeniya` (дата и время проведения)
- `mesto_provedeniya` (место проведения)
- `fio_comissara` (ФИО комиссара)
- `comissar_id` (ссылка на военного комиссара, внешний ключ)

Для реализации связи многие-ко-многим предусмотрена промежуточная таблица **Prizivnik_Comissar**. Она содержит поля:
- `prizivnik_id` (ссылка на призывника, внешний ключ)
- `comissar_id` (ссылка на комиссара, внешний ключ)
- `data_vzaimodeistviya` (дата взаимодействия)
- `nomer_kabineta` (номер кабинета)

Для реализации связи многие-ко-многим предусмотрена промежуточная таблица **Prizivnik_Meropriyatie**. Она содержит поля:
- `prizivnik_id` (ссылка на призывника, внешний ключ)
- `meropriyatie_id` (ссылка на мероприятие, внешний ключ)

Ниже приведены SQL-запросы для создания всех таблиц по теме «Военкомат»:

### ПРИЗЫВНИКИ

```sql
CREATE TABLE public.prizivnik (
    id_prizivnik integer NOT NULL,
    fio character varying(255) NOT NULL,
    data_rozhdeniya date NOT NULL,
    adres_prozhivaniya text,
    nomer_pasporta character varying(20) NOT NULL,
    id_voennogo_bileta integer,
    id_voenno_uchetnoi_karty integer
);
```

### КОМИССАРЫ

```sql
CREATE TABLE public.comissar (
    id_comissar integer NOT NULL,
    fio character varying(255) NOT NULL,
    dolzhnost character varying(100) NOT NULL,
    stazh_raboty integer,
    kontaktnyi_telefon character varying(20)
);
```

### ВОЕННО-УЧЁТНЫЕ КАРТЫ

```sql

    id_karty integer NOT NULL,
    nomer_karty character varying(50) NOT NULL,
    data_postanovki_na_uchet date NOT NULL,
    istoriya_otsrochek text,
    voenno_uchetnaya_specialnost character varying(100),
    id_prizivnika integer NOT NULL
);
```

### МЕДИЦИНСКИЕ ОСВИДЕТЕЛЬСТВОВАНИЯ

```sql
CREATE TABLE public.med_osvidetelstvovanie (
    id_osvidetelstvovania integer NOT NULL,
    data_provedeniya date NOT NULL,
    rezultaty_obsledovania text,
    fio_vracha character varying(255) NOT NULL,
    zaklyuchenie text,
    id_prizivnika integer NOT NULL,
    id_kategorii integer NOT NULL
);
```

### КАТЕГОРИИ ГОДНОСТИ

```sql
CREATE TABLE public.kategoria_godnosti (
    id_kategorii integer NOT NULL,
    nazvanie_kategorii character varying(1) NOT NULL,
    opisanie_ogranichenii text,
    index_kategorii character varying(10),
    osnovanie_dlya_kategorii text,
    CONSTRAINT kategoria_godnosti_nazvanie_kategorii_check 
        CHECK (((nazvanie_kategorii)::text = ANY (
            (ARRAY['А'::character varying, 'Б'::character varying, 
                   'В'::character varying, 'Г'::character varying, 
                   'Д'::character varying])::text[]
        )))
);
```

### ВОЕННЫЕ БИЛЕТЫ

```sql
CREATE TABLE public.voennyi_bilet (
    id_bileta integer NOT NULL,
    nomer_bileta character varying(50) NOT NULL,
    data_vydachi date,
    voinskoe_zvanie character varying(50),
    kategoria character varying(50),
    id_prizivnika integer NOT NULL
);
```

### ПРИЗЫВНЫЕ МЕРОПРИЯТИЯ

```sql
CREATE TABLE public.prizivnoe_meropriyatie (
    id_meropriyatiya integer NOT NULL,
    tip_meropriyatiya character varying(100) NOT NULL,
    data_provedeniya timestamp without time zone NOT NULL,
    mesto_provedeniya text,
    fio_comissara character varying(255),
    id_comissar integer NOT NULL
);
```

### СВЯЗЬ ПРИЗЫВНИК-КОМИССАР

```sql
CREATE TABLE public.prizivnik_comissar (
    id_prizivnik integer NOT NULL,
    id_comissar integer NOT NULL,
    data_vzaimodeistviya date,
    nomer_kabineta character varying(10)
);
```

### СВЯЗЬ ПРИЗЫВНИК-МЕРОПРИЯТИЕ

```sql
CREATE TABLE public.prizivnik_meropriyatie (
    id_prizivnik integer NOT NULL,
    id_meropriyatiya integer NOT NULL
);
```

## 4 ДРУГИЕ SQL-КОМАНДЫ

При работе с базами данных часто возникает необходимость изменять структуру таблиц, не теряя имеющиеся данные. Для этого используется оператор `ALTER TABLE`, который позволяет переименовывать столбцы, изменять их типы, а также добавлять или удалять ограничения. Эти возможности позволяют гибко адаптировать схему базы данных под изменяющиеся требования.

Например, если необходимо переименовать столбец, чтобы сделать его название более понятным, можно использовать следующую команду (в нашем случае для таблицы `med_osvidetelstvovanie`):

```sql
ALTER TABLE med_osvidetelstvovanie 
    RENAME COLUMN rezultaty_obsledovania TO rezultaty_medosmotra;
```

В случаях, когда требуется изменить тип данных, например можно сделать:

```sql
ALTER TABLE prizivnik
    ALTER COLUMN stazh_raboty TYPE SMALLINT
    USING stazh_raboty::SMALLINT;
```

Ограничения (constraints) в SQL обеспечивают контроль за целостностью данных. Они позволяют задать строгие правила для столбцов, такие как `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY` и `CHECK`.

Например, добавим ограничение `CHECK`:

```sql
ALTER TABLE kategoria_godnosti
    ADD CONSTRAINT chk_kategoria_valid
    CHECK (nazvanie_kategorii IN ('А','Б','В','Г','Д'));
```

Если возникает необходимость сделать нечто уникальным, например email клиента:

```sql
ALTER TABLE prizivnik
    ADD CONSTRAINT ux_prizivnik_pasport UNIQUE (nomer_pasporta);
```

Таким образом, оператор `ALTER TABLE` позволяет эффективно управлять структурой базы данных, обеспечивая гибкость и поддержку целостности данных.

## 5 СОЗДАНИЕ ВРЕМЕННОЙ ТАБЛИЦЫ

Создадим временную таблицу `tmp_priziv_report` и заполним ее данными:

```sql
CREATE TEMP TABLE tmp_priziv_report AS
SELECT
    kg.nazvanie_kategorii AS kategoria_godnosti,
    kg.opisanie_ogranichenii AS opisanie_kategorii,
    COUNT(p.id_prizivnik) AS kolichestvo_prizivnikov,
    COUNT(CASE WHEN mo.id_kategorii = kg.id_kategorii THEN 1 END) AS proshli_medosmotr
FROM kategoria_godnosti kg
LEFT JOIN med_osvidetelstvovanie mo ON kg.id_kategorii = mo.id_kategorii
LEFT JOIN prizivnik p ON mo.id_prizivnika = p.id_prizivnik
GROUP BY kg.id_kategorii, kg.nazvanie_kategorii, kg.opisanie_ogranichenii
ORDER BY kolichestvo_prizivnikov DESC;
```

Сделаем выборку:

```sql
SELECT * FROM tmp_priziv_report;
```
